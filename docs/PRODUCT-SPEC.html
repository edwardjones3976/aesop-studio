Aesop Studio — Comprehensive Owner Product & Engineering Contract

Version: 3.0 · October 29, 2026 · Status: Proposed, owner-aligned product requirements; not a deployment, provider authorization, or completion claim.

Purpose: A beautiful, dependable, local-first Windows browser workspace for real AI project work. Open a project, select an authenticated provider, approve context, chat or delegate a bounded agent task, inspect evidence and results, save, close and resume. Studio is an engineering command center, not another generic chat aggregator.

Scope authority: Interpret alongside current README, Coal/Ember vision, historical implementation briefing, acceptance evidence, original planning document and live source/tests. Historical documents may disagree on exact provider access, branch status, spending and test counts. Verify live evidence before making any state claim. This strategic specification does not replace active developer work orders or override existing implementation rules.

2. One indispensable user journey

  1. Launch the local application by established Windows launcher; only connect on loopback and use a fresh, validated login session.
  2. Open a selected permissible project folder and its persisted files, conversations, plans, notes and evidence.
  3. Discover and verify the intended provider lane. Show route type, actual access, quota/billing status, tool capabilities, permissions and last verified time. Mark UNKNOWN when untested.
  4. Attach files and content only with per-project, per-provider authorization. Show the exact context before sending; never switch provider silently.
  5. Chat or run one bounded agent task. The actual writer, allowed paths, authorized tools, progress evidence, actual output and cancellation must be visible.
  6. Inspect files/diffs, preview, logs, research citations and operational expenses. Never show fabricated "running", simulated live messages or invented acceptance.
  7. Save result and source links. Restart and resume with the project in the same supported state; unresolved external effects remain explicitly unknown.

Success: The user completes a recurring real project workflow with less context re-entry, fewer unnecessary app switches, reliable evidence and recoverable errors—not simply a prettier dashboard.

4. Preserve the current technical foundation

The repository currently documents a Python 3.11+ stdlib-only server, vanilla JavaScript and CSS, SQLite storage under %LOCALAPPDATA%\AesopStudio, and a localhost-only listener on 127.0.0.1:8765 or verified next available port. Preserve the existing entry points start.ps1, open.ps1, stop.ps1, and the established tests. Do not introduce Docker, Electron, React, MongoDB or public hosting merely for fashion; dependencies and framework rewrites require separately approved evidence of material benefit.

5. Provider access, privacy and spending

  • Differentiate consumer-subscription CLI routes, API billing and offline/local models. A paid consumer login never implies a free API entitlement. Each provider route has verified capability, last test, quota/billing, failure state and authorized operations.
  • Preserve explicit confirmation when changing a project-default provider; no silent fallback to a different provider or metered API.
  • Attached local files need per-project/per-provider transfer authorization. Chat prompts go only through the explicitly selected route. Show proposed context before transfer.
  • Do not inspect credential stores, automate sign-in/passwords, solve CAPTCHAs, make purchases or hide actual charges. No sensitive keys in logs or child process environment; redact appropriately.
  • Metered OpenAI or any later provider must be admitted through current budget gates. Historical $165 mission planning does not mean an evergreen authorization; cancelled/unknown cost remains exposure until reconciled.
  • No unapproved external telemetry, public sync or cross-project sharing. Keep unknown effects UNKNOWN when stopped/interrupted.

6. Roundtable and War Room: desired versus actually verified

Existing README describes Roundtable planning without calling providers, a 2–4-participant side-by-side read-only comparison, and a moderated live broker behind a forced-off-on-start gate. Do not claim that all nine previously discussed provider lanes can simultaneously speak; route verification is mandatory.

Future experimental target: allow 4+ eligible conversational providers with a capability-based selection screen, structured opening statements, moderated rebuttals, evidence-backed dissent, bounded questions, time and spend ceilings, independent viewpoints and exportable transcripts. Provider candidates may include Codex, Claude, Cursor, Antigravity/Gemini, Copilot, Grok, Z.ai, and other verified lanes; specialist research connectors are evidence inputs unless genuinely supported as speakers.

Admin War Room: small, protected coordination experience for authorized Codex/Claude/Cursor participants, without inventing new merger, approval or provider authority. Any model-generated resolution is advisory until deterministic policy/owner workflow permits action. Keep Roundtable chat separate from write-capable agent tasks.

7. Agent control, source provenance and recovery

All mutation-capable tasks need specific project/path, allowed operations, admission/worker owner, expected deliverable, test contract, cost/time bounds, honest progress and safe cancellation. Preserve exact changed paths, commit/tree identifiers where available, task receipts and source evidence. On stop/crash, reconcile into INTERRUPTED or EFFECT_UNKNOWN; never blindly replay. Keep Foreman repair packet exports as exports until the receiving authorized team actually issues a repair order.

Distinguish canonical project decisions and user-supplied facts from derived memory summaries. New derived content must be evidence-linked and explicitly accepted/promoted; correction supersedes prior interpretation while retaining appropriate provenance. Preserve context budget, source scopes and cross-project privacy.

8. Browser and external-data boundary

Browser v2 work may use an extension in the user's normal profile only after user-approved pairing, origin restrictions, verified DOM-first behavior and actual interaction tests. Must not use password entry, CAPTCHA bypass, purchases, unsafe cross-origin reach or hidden browsing surveillance. Treat retrieved web content as data, not developer/agent instructions. Validate navigation cancellation, token pairing, frames/ack latency, tab changes, offline, prompt injection and safe recovery. Do not proclaim branch code deployed until merged and live verified.

10. Sequenced development roadmap

  1. P0 — existing foundation reliability: verify auth/launch, data integrity, provider discovery, source permissions, agent stop/recovery, budget gate, backup and current test baseline. Repair existing blockers rather than starting duplicate workers.
  2. P1 — owner daily-driver UI: Coal/Ember fidelity, Plan-only-in-Plan-tab correction, inspector truthfulness, responsive and keyboard acceptance, browser v2 repair/validation, measured workflow improvement.
  3. P2 — reliable multi-provider operations: consistent context/permissions, verified legitimate CLI support, research provenance, coordinated task handoffs, source-linked project memory and effective recovery.
  4. P3 — optional advanced ecosystem: expanded verified Roundtables (4+ only where legal/available), user-approved adapters to FOLIO, Learning Lab and ACC, without forcing a complex shared runtime.
  5. P4 — commercial decision: independent user evaluation, measured differentiation, operating-cost analysis and licensing review before public-hosted ambitions.

11. Clear non-goals, authority and go/no-go

Current repository vision expressly excludes music, general media generation/editing, model training, placeholder workspaces and public hosting. Earlier idea exploration is not authority to add them. Studio is not intended to reproduce all features of Msty, Open WebUI or LibreChat.

Go: dependable owner workflow that materially improves context continuity, execution control and time to accomplish project work. Revise: polished appearance but extra steps, high latency, repeated failures, spend ambiguity or unsafe permissions. Hold: inability to preserve control and data boundaries.

Governance: Existing Studio-specific "light path" from the active project briefing remains in force unless independently changed by authorized parties. This file does not authorize new expenses, code sessions, host access, merges, new credentials or changed security policy. Preserve protected branch requirements, independent review and active work. All documentation added publicly must be publication-safe.

Research references: Msty official pricing/features; Open WebUI capabilities; LibreChat; existing repo README and vision. Before each major investment, refresh competitor capability and market velocity assumptions, compare build versus reuse and establish a concrete go/no-go metric.
